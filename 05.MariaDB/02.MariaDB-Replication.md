## MariaDB Replication:

Replication lets one server (primary/master) send binary log events to one or more replicas (slaves). It's best suited for read scaling, live backup for disaster recovery, and analytics.


### Architecture: 

| Node | IP             | Role   |
| ---- | -------------- | ------ |
| DB1  | 192.168.10.192 | Master |
| DB2  | 192.168.10.193 | Slave  |

## Master Configuration:

### Edit config file:

Edit` /etc/my.cnf` or `/etc/my.cnf.d/server.cnf`:

```conf
[server]

[mysqld]

[galera]

[embedded]


[mariadb]
server-id=1
log_error

# Binary logging — required for replication
log_bin=mariadb-bin
log_basename=master1   # avoids issues if hostname changes

# Optional but recommended:
binlog_format=mixed 
expire_logs_days=7
max_binlog_size=100M


[mariadb-10.11]

```


_Restart MariaDB:_
```
systemctl restart mariadb
```



### Create replication user:

```
CREATE USER 'repl'@'%' IDENTIFIED BY 'repl#2026';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';
FLUSH PRIVILEGES;
```


```
show grants for 'repl'@'%';
```

## Slave Configuration:

### Edit config file:

Edit` /etc/my.cnf` or `/etc/my.cnf.d/server.cnf`:

```conf
[server]

[mysqld]

[galera]

[embedded]


[mariadb]
server-id=2
log_error

log_bin=mariadb-bin
log_basename=replica1

relay_log=relay-bin
read_only=ON   # Prevent writes on replica


[mariadb-10.11]

```


_Restart MariaDB:_
```
systemctl restart mariadb
```

### Configure Slave Replication: 

Every transaction on the primary gets a unique ID:

```
0-1-100
│ │  └── Transaction number
│ └──── Server ID
└────── Domain ID
```


#### `slave_pos` — Replica tracks its own position:

- Uses the system variable `gtid_slave_pos`
- Tracks only transactions received **via replication**
- ✅ Safer — recommended for **existing replicas** already replicating
- ✅ Ignores any local writes done directly on replica


#### `current_pos` — Replica uses combined position:

- Uses `gtid_current_pos` = combination of `gtid_slave_pos` + `gtid_binlog_pos`
- Includes both replicated transactions AND local writes
- ✅ Good for **fresh replica** with no prior local writes
- ⚠️ Risky if replica had **any local writes** — can cause conflicts


#### Simple Comparison:

| - | slave_pos | current_pos |
| - | --------- | ----------- |
| Tracks | Replicated transactions only | Replicated + local writes |
| Best for | Existing replica | Fresh/new replica |
| Risk | Low | Higher if local writes exist |
| Recommended |✅ Most cases |⚠️ Fresh setup only |



_Traditional (binlog file + position):_
```
CHANGE MASTER TO
MASTER_HOST='192.168.10.192',
MASTER_PORT=3306, 
MASTER_USER='repl',
MASTER_PASSWORD='repl#2026',
MASTER_LOG_FILE='master1-bin.000001',
MASTER_LOG_POS=769;
```


_Or, GTID-based:_ 
```
CHANGE MASTER TO
MASTER_HOST='192.168.10.192',
MASTER_PORT=3306, 
MASTER_USER='repl',
MASTER_PASSWORD='repl#2026',
MASTER_USE_GTID = current_pos; -- fresh replica  

-- Or:
MASTER_USE_GTID = slave_pos; -- For an existing replica already replicating
```





### Useful Monitoring Commands: 

```
-- On primary
SHOW MASTER STATUS;
SHOW PROCESSLIST;


-- On replica
SHOW SLAVE STATUS\G
STOP SLAVE;
START SLAVE;

RESET SLAVE ALL;   -- completely remove replica config


-- Check GTID state
SELECT @@gtid_current_pos;
SELECT @@gtid_slave_pos;
```

## Troubleshooting:


Your user (`root`) has the **SUPER** privilege. `read_only=ON` does NOT block SUPER users. Most likely you're logged in as `root`, which has **SUPER** — so `read_only` is effectively ignored for that session.

```
SELECT USER(), CURRENT_USER();
```


```
SHOW GRANTS FOR CURRENT_USER();
```



### On Slave:

_Fix the on Slave:_
```
STOP SLAVE;

RESET SLAVE ALL;
```
